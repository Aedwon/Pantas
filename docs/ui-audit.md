# UI Audit

Running log of hands-on UI findings, in the spirit of `content/audit/` but for
the app surface rather than the corpus.

Severity follows the content audit: **[blocker]** ships broken, **[important]**
noticeably wrong, **[polish]** cosmetic. Status is one of OPEN, FIXED, or
DECISION NEEDED.

## Method and environment

Manual passes driven on the `pantas_pixel` Android emulator
(`flutter run --flavor dev -t lib/main_dev.dart`), Flutter 3.44.6.

**Caveat for anyone reproducing these:** the pass on 2026-07-25 ran against a
temporary `assets/seed/v1.json` generated by `tools/build_dev_seed/` from
`content/questions/` and `content/lessons/` — 1,115 questions and 141 lessons
under a single UPCAT exam. That seed is throwaway scaffolding for UI/UX work,
not shipping content, and it breaks two expectations in
`test/core/storage/data/seeder_test.dart` that assume the 2-subject demo seed.
It is therefore left uncommitted on purpose — `assets/seed/v1.json` is a
shipping asset, so the committed copy stays the demo seed. Regenerate it with
`dart run tools/build_dev_seed/build_dev_seed.dart` and discard it with
`git checkout -- assets/seed/v1.json`.
Findings below that depend on real content volume are marked as such.

## Findings from manual passes

### UI-001 [blocker] Screens with no back or exit control — FIXED

Reported 2026-07-25: "there are a lot of instances where I can't go back
because the back/exit button doesn't exist."

Confirmed and traced to a single root cause. `context.go()` **replaces** the
go_router stack, so the destination's `AppBar` has nothing to pop and renders
no back arrow. For routes outside the `StatefulShellRoute` the bottom tab bar
is absent too, leaving no on-screen exit at all — Android system back then
quit the app outright (verified from `/plan`).

Affected: today's session, quick quiz, retake, drill, drill-subtopic browser,
study plan, quiz results, assessment, assessment results, and — via private
`_go` helpers wrapping `router.go()`, which a `context.go(` search misses —
the entire Settings subtree plus the legal Privacy/Terms pages.

Two aggravating details:

- `quiz_page.dart` set `leading` **only** while `QuizRunning`, so the loading,
  error and empty states had no control at all. An empty drill (a topic with
  no authored questions) offered nothing but a "Retry" that could never
  succeed.
- Delete Account's "Cancel" calls `Navigator.maybePop()`, a silent no-op once
  `go()` had emptied the stack.

**Fixed** by converting those call sites to `context.push`, giving
`quiz_page` an unconditional `leading` (close-with-confirm while running,
plain back otherwise), and using `pushReplacement` for assessment → results so
back does not re-enter a completed run. The standing rule is now: navigate
outside the tab shell with `push`, never `go`; reserve `go` for tab switches
and deliberate flow resets such as `/onboarding`.

### UI-002 [polish] Elastic overscroll at the top and bottom of pages — CLOSED, NO CHANGE

Reported 2026-07-25: "when pulling down from the top or pulling up from the
bottom the page becomes elastic."

**This is current Android platform behaviour, not a defect.** The app sets no
`ScrollBehavior` or `ScrollPhysics` anywhere in `lib/`, so it inherits
Flutter's `MaterialScrollBehavior`. With `useMaterial3: true`
(`app_theme.dart:28`) on Android that resolves to:

- `ClampingScrollPhysics` — the scroll *position* stops hard at the edge, and
- `StretchingOverscrollIndicator` — the *content* stretches while you pull.

(Source: `material/app.dart:879-898` and
`widgets/scroll_configuration.dart:243-252` in the Flutter SDK.)

The stretch is what Android 12 (API 31) introduced to replace the older blue
edge glow. Google's own apps behave this way, and Flutter already picks the
correct idiom per platform automatically — iOS builds get `BouncingScrollPhysics`
rubber-banding instead, which is equally the norm there.

So the literal request — "use what the industry does" — is satisfied by
changing nothing. The real question is whether Pantas should deliberately
*deviate* from platform convention, which is a design call rather than a bug
fix:

| Option | Behaviour | Trade-off |
|---|---|---|
| **A. Keep defaults** (recommended) | Stretch on Android, bounce on iOS | Native on both; zero code; users get what every other app on their phone does |
| **B. Suppress the indicator** | `ScrollBehavior.copyWith(overscrollIndicator: false)` — hard stop, no visual | Feels tight and deliberate, suits the Ink & Rule identity; non-native, and removes the only feedback that you have reached the end |
| **C. Force bouncing everywhere** | iOS rubber-band on Android too | Consistent across platforms; actively wrong on Android and often reads as "this is an iOS port" |

If the objection is specifically that the stretch looks bad against the fixed
page headers, that is worth a targeted look before reaching for a global
override — the effect is per-`Scrollable`, so it can be tuned in one place
without changing platform behaviour app-wide.

**Decision (2026-07-25, Aedwon): option A — keep the defaults.** No code
change. Pantas follows platform overscroll convention: stretch on Android,
bounce on iOS. Do not add a `ScrollBehavior` or `ScrollPhysics` override to
"fix" this; if it comes up again, it is working as intended.

### UI-008 [polish] Assessment results appear with no sense of processing — OPEN

Reported 2026-07-25, while answering the assessment on the emulator: the
results screen arrives the instant the last question is answered. Nothing
signals that the app weighed the answers, so the grading reads as
instantaneous — and therefore as if nothing was computed.

Wanted: a brief loading screen or animation between the final answer and the
results, framing the moment as "we are working out where you stand." The
computation itself is local and effectively instant, so this is deliberate
pacing rather than a progress report — it should be honest about that (a short
beat, not a fake multi-second progress bar).

Note the sequencing constraint: this sits between `assessment_page` and
`assessment_results_page`, which are joined by `pushReplacement` (see UI-001,
so back does not re-enter a completed run). Any interstitial has to preserve
that, or back-from-results starts landing on the loading screen.

### UI-009 [polish] Bottom navigation is text-only — DECISION NEEDED

Reported 2026-07-25: "there should be icons in the bottom navigation. they
look so bland currently."

**Working as specified — but the specification is the thing being questioned.**
`app_shell.dart` draws four `Text` labels on a hairline-topped bar with no
icons. That is deliberate:
`docs/superpowers/plans/2026-07-19-ink-and-rule-reference-sweep.md:266` and
`:389` both say "text-only labels per the approved mock", and every home mock
in `.superpowers/brainstorm/73545-1784382720/content/` (`direction.html`,
`direction-v2.html`, `direction-v3.html`) draws the bar the same way. So this
was seen and approved, not overlooked.

The identity does not ban icons outright — the header gear, `InkTableRow`
glyphs and the done ✓ all survive. What the spec bans is "icon-in-tinted-circle
headers" and "emoji-as-icon". A hairline outline glyph is not obviously outside
that. The real cost is that Material's stock icon set is exactly the geometric
vocabulary the redesign set out to escape, so `Icons.home_outlined` and friends
would pull the bar back toward the look being replaced.

| Option | Behaviour | Trade-off |
|---|---|---|
| **A. Keep text-only** | Unchanged | Free; matches the approved mock; the bar stays quiet and editorial. Aedwon's objection stands unanswered |
| **B. Add restrained outline icons** | 20px `Icons.*_outlined` above each label, `inkMuted`/`ink` | Conventional and scannable; risks reading as stock Material, the exact failure mode the redesign names |
| **C. Serif rule marks instead of icons** | A short board-green rule under the active label, or a serif glyph per tab | Keeps the identity, adds the visual anchor the bar lacks; bespoke, and needs its own mock round |

Recommend **C** as the smallest change that answers the complaint without
reopening the identity. Whatever wins, it amends the approved mock — record the
decision in the redesign spec's Amendments section, not only here.

**Decision (2026-07-25, Aedwon): icons, resolved against live mockups.** The
complaint was recognition speed, not decoration, which ruled out the rule-mark
option: a decorative marker does nothing for how fast a thumb finds the right
tab. Settled spec — 23px glyphs at **1.50** stroke; active state is the **filled
glyph** (no rule break, no board green, so the colour budget is untouched);
transition is an **ink rise** over **400ms** on the incoming tab only, disabled
under reduce-motion. Glyphs: house, open book, single shaded answer bubble,
folded sheet with a rising line. Full rationale in
`docs/superpowers/specs/2026-07-26-home-and-navigation-design.md`.

### UI-010 [important] Home greeting names the exam, not the user — OPEN

Reported 2026-07-25: "in the topmost part it says Magandang gabi, UPCAT which
is wrong. aren't we supposed to get an input for the user's name/nickname for
this?"

**Confirmed, and it is a known deviation rather than a bug introduced by
accident.** `assessment_home_tab.dart:105` renders `examShortName` in the serif
masthead slot. The approved mock (`header-final-v2.html`) reads
"Magandang gabi," over **"Aedwon"** — a personal name. The redesign spec says
the same: "Left block: kicker ("Magandang gabi,") over serif **name**."

The reference-sweep plan recorded the substitution deliberately at
`2026-07-19-ink-and-rule-reference-sweep.md:614`: "the masthead is the exam
name for now — personal-name greeting waits for the auth surface, noted
deviation from the mock."

The blocker is real but narrower than "wait for auth". Nothing in the app
captures a name a user typed. The only name that exists anywhere is
`AuthUser.displayName`, which comes from Google sign-in and is read in one
place, `account_page.dart:47`. Signed-out users have no name at all, so an
auth-only greeting leaves the masthead empty for everyone who has not signed
in — which is the entire onboarding path.

So this needs a decision on *where the name comes from* before it can be
fixed:

| Option | Source | Trade-off |
|---|---|---|
| **A. Ask during onboarding** (recommended) | A nickname step writing to `UserSettings` | Works signed-out; one more onboarding step to justify; needs a Settings row to change it later |
| **B. Settings only, no onboarding step** | A "Your name" row in `settings_home_page` | Zero onboarding friction; almost nobody sets it, so the masthead stays the exam name in practice |
| **C. Use `AuthUser.displayName` when present** | Google account | No new input at all; blank for signed-out users, and the name is whatever Google holds, often a full legal name |

A and C compose — ask in onboarding, prefill from the Google account when
already signed in. Note the storage question either way: `UserSettings` has no
name field today (`lib/features/settings/domain/user_settings.dart`), so this
adds a settings key, not just a widget.

Related: the onboarding polish plan
(`docs/superpowers/plans/2026-07-25-onboarding-polish.md`) has 13 tasks and
none of them capture a name. If option A wins, that plan gains a task.

**Decision (2026-07-25, Aedwon): option A, no Google prefill.** A name step is
added to onboarding **after the exam picker**, so the ask lands once the user
has already invested. No prefill from `AuthUser.displayName` — the name is
chosen, not assumed. Users with no name stored (every existing install, plus
anyone who skips) see an **"Add your name" invitation** in the masthead slot
that taps through to set it, which is self-healing and needs no migration
prompt.

**Follow-on discovered while designing the masthead: the exam date is never
captured either.** Onboarding is `welcome → ageGate → picker` and never touches
`examDate`; the Settings row that would set it is unwired (onboarding-polish
Task 6, unexecuted). So `examDate` is null for every user today, and the
approved masthead line "UPCAT · 42 days to go" cannot render for anyone. An
exam-date step belongs beside the name step. This also blocks the days-to-exam
figure in UI-011.

### UI-011 [important] Home shows one section — three of the mock's four blocks are unbuilt — OPEN

Reported 2026-07-25: "is the focus topic the only thing shown in the home? it
feels so empty... i assume it's because we now have a dedicated progress tab
which moved the supposed content to that side."

**The emptiness is real. The explanation is not.** The Progress tab took
nothing from Home — it replaced the old *Settings* tab as branch 4
(`2026-07-19-ink-and-rule-reference-sweep.md:257`, "Progress in, Settings
out"), and its panels are Spec 11 material (archetype, streak, coverage,
analytics) that Home never carried. Nothing moved; the missing blocks were
never built.

The approved mock (`direction-v3.html`) composes Home from four blocks:

1. Header + stats band — **three** figures: 42 days to exam, 78% accuracy,
   41/96 lessons
2. **Today's plan** — "2 of 3 done", three lesson rows, "Continue lesson"
3. **Up next** — two queued lesson rows
4. **Weakest areas** — "Practice these" + accuracy rows

Shipped Home has block 1 with **two** of its three figures, and block 4 under
the name "Focus topics". Blocks 2 and 3 are absent. Every gap traces to an
unwired data chain, each already recorded:

- *Days to exam* — `UserSettings.examDate` exists and
  `DriftSettingsRepository.updateExamDate` validates it, but **no UI writes
  it** (onboarding-polish Task 6 is unexecuted) and Home never reads it.
- *Lessons done* — no lesson-count provider exists anywhere in `lib/`.
- *Today's plan / Up next* — study-plan providers are throwing stubs. This is
  UI-003, the same root cause that got the `/plan` row hidden.

Both stats gaps were declared, not forgotten:
`2026-07-19-ink-and-rule-reference-sweep.md:600` — ""Days to exam" and "lessons
done" figures are DEFERRED to the data plan... **do not fake them**."

**The gap worth flagging: "the data plan" does not exist.** Three plan
documents defer work to it — days-to-exam, lessons count, per-subject accuracy,
the Progress tab's real analytics — and no such plan has been written. Home
stays a third of its mock until it is. That plan, not a Home patch, is the fix
for this finding; patching Home alone would mean faking figures the sweep
explicitly forbade.

Sequencing note: onboarding-polish Task 6 is a prerequisite for the
days-to-exam figure and is already written and unexecuted, so it is the
cheapest first move.

**Decision (2026-07-25, Aedwon): build the cheap tier now, defer "Today's
plan".** Home gets the full three-figure stats band (days to exam, accuracy,
lessons), the "Lately" line, an "Up next" block, and the weakest-areas rows.
Every one of those reads tables the app already writes:

- *Days to exam* — `UserSettings.examDate` minus today, once onboarding-polish
  Task 6 ships the picker that writes it.
- *Lessons done* — `lesson_progress_local` (one row per lesson, with `readAt`)
  counted against `lessons` for the active exam.
- *Up next* — unread lessons in the weakest topics: the same two tables asked a
  different question.

**"Today's plan" is explicitly out of scope** and does not render at all until
the study-plan feature is real. It is the one block that cannot be derived from
stored data — a daily plan has to decide how much a user should do today and
track completion, which is mastery scoring, review scheduling and daily
targets. That remains its own project, tracked as UI-003.

Home composition beyond this block list was still being explored when this
decision was recorded; see the design spec for the settled layout.

### UI-012 [blocker] Focus-topic taps still strand the user — UI-001 missed two call sites — OPEN

Found 2026-07-26 while mapping where each Home block navigates to, for the Home
redesign.

`assessment_home_tab.dart` navigates with `context.go` in two places:

- line 242 — `_FocusTopicRow.onTap`
- line 209 — the "Continue studying" button

Both send the user to `_studyPath(mastery)`, which returns
`/study/topic/:topicId` when the topic is weak but **`/quiz/quick/:examId` when
the topic is `strong`**. `/study/topic/:topicId` is nested inside the Study
`StatefulShellBranch` (`router.dart:99-110`), so `go` is correct there — it is a
tab destination and keeps the tab bar. `/quiz/quick/:examId` is a **top-level
route outside the shell** (`router.dart:163`), so `go` empties the stack: no
back arrow, no tab bar, and Android back quits the app.

This is UI-001 exactly, in a file the UI-001 sweep touched. It survived because
the path is *computed* by `_studyPath` rather than written inline, so the
`context.go('/quiz` search that found the other call sites missed these two. The
same file gets it right at line 302 with `context.push('/quiz/quick/$examId')`.

Only reproducible once a topic reaches `MasteryLevel.strong`, which is why
manual passes have not hit it.

**Fix:** `push` for the quiz branch of `_studyPath`, `go` for the study branch —
the destination decides, not the call site. Worth extracting the choice into a
helper so the rule cannot drift again, and worth a regression test that asserts
a strong-mastery row pushes rather than replaces.

### UI-013 [important] The share card was missed by the Ink & Rule sweep — OPEN

Found 2026-07-26 while discussing Pro card variants.

`wrapped_share_card.dart:27` renders the shareable 9:16 card as a **purple and
navy gradient** (`0xFF16213E`, `0xFF533483`, `0xFF0F3460`) with white text. That
is pre-redesign styling, and specifically a gradient, which
`2026-07-18-ui-redesign-design.md` lists among the telltale patterns the
identity exists to eliminate ("gradient/glow decoration").

The Ink & Rule feature sweep covered `wrapped_reveal_page.dart`,
`my_shared_cards_page.dart` and `share_privacy_sheet.dart`, but neither
`wrapped_share_card.dart` nor `wrapped_png_renderer.dart` appears anywhere in
`2026-07-19-ink-and-rule-feature-sweep.md`. The chrome around the card was
restyled; the card itself was not.

**Why this ranks above a normal polish item:** the share card is the only asset
seen by people who do not have the app. `2026-06-10-user-facing-metrics-design.md`
calls it "the app's marketing engine", and the landing-page spec builds a whole
conversion funnel on the shared PNG. Every screen behind the paywall now carries
the identity while the billboard does not.

Not currently visible to users, because the Wrapped surface is unreachable
(UI-004). It becomes visible the day artifacts are wired up, which is also the
day it is hardest to change quietly.

**Fix:** sweep both files onto the Paper/Ink palette and the serif figure
treatment before Wrapped ships. Worth doing as its own pass, since the card is
a fixed-size rendering target rather than a responsive screen and needs
checking as an exported PNG rather than on the emulator.

### UI-004 [polish] Latent dead end at `/wrapped/:artifactId`

`notification_tap_router.dart:63` navigates with `go()`, and
`wrapped_reveal_page` defines no `leading`. Currently unreachable, because the
wired `planReader` in `notifications_providers.dart:31` is hardcoded to

### UI-005 [important] Inline math sits below the baseline

`portable_text_renderer.dart` renders inline LaTeX as a `WidgetSpan` with no
`alignment`, so every inline `$x$`, `$m$`, `$<$` drops subscript-low in the
middle of a sentence. Highly visible in mathematics and science lessons.
Depends on real content — invisible with the demo seed.

### UI-006 [important] Numbered solution steps all render as "1."

`portable_text_renderer.dart` clears its list counters on any non-list block.
In worked solutions a display-math block sits between each step, so every
solution reads "1. 1. 1. 1." rather than 1, 2, 3, 4. Depends on real content.

### UI-007 [important] Question stems render markdown and LaTeX literally

`question_card.dart:22` is a plain `Text`. A Filipino vocabulary item displays
`Ang **pagtitiis** niya` with the asterisks showing, and 237 questions in the
generated seed carry `$…$` LaTeX that appears raw. The v1 schema stores stems
as plain text columns with no rich-text representation, so this is a schema
question as much as a rendering one.

## Home

### UI-012 [important] The bottom navigation icons
> "the navbar icons are wrong and outdated"

**The claim under this finding was wrong when it was written.** It said the bar
carried stock Material icons. It has carried the bespoke painted glyphs since 9
August. Aedwon was looking at the approved design and still called it wrong,
which is the more useful fact and was buried by a mistaken diagnosis.

**Resolved 10 August, and he was right twice.**

> "for the navbar icons: i replaced again especially the quiz icon. it's in the
> docs. please thoroughly check. also i don't think the Home icon is right"

**First: the quiz glyph was decided twice and the second decision was never
built.** The single shaded bubble was specced on 26 July. **A second round ran
on 28 July**, `quiz-glyph-v2.html`, whose whole premise was that a circle is
wrong beside the other three: *"A circle has no internal structure. At 23px
beside three structured objects it reads as a dot."* His selection is recorded
in that session's log at the last timestamp: **S1, "Three options and rules"**,
with the note *"looks natural"*. The bubble was built anyway.

**Now built as chosen:** three options with their rules, and **only the middle
one shades**. The ink rise survives intact, because ink rising into one bubble
is still a pencil shading an answer.

**Second, the Home glyph, and this one runs through all four.** Every mockup
draws the house **with a doorway**. The implementation drew the outer pentagon
and nothing else. Checking the other three found the same omission each time:

| Glyph | The mockups draw | What was built |
|---|---|---|
| Home | Walls, roof, **and a doorway** | The silhouette only |
| Study | Two leaves **and a spine** | One outline, no spine |
| Progress | Sheet, **folded corner**, rising line | Sheet and line, no fold |
| Quiz | (superseded, see above) | The old bubble |

**This is what "outdated" was pointing at.** The v2 round names the thing
exactly: each glyph is meant to be an object with internal structure, *"a roof
and a doorway, a spine and two leaves"*. Drawn as bare silhouettes they are
blobs, and filled solid on the active tab they are worse.

**A third defect fell out of the same reading.** The progress sheet's rising
line was in the same path as its body, so the ink rise filled it: a stroke
meant to be a line was being printed as a solid wedge. The fill region and the
stroked outline are separate now, which is also what lets the quiz shade one
bubble of three.

**Seven tests cover the shapes**, counting the parts of each glyph and
asserting the quiz fills one option rather than all of them.

**What I got wrong:** I read the specs and the audit and reported the glyphs as
correct and the disagreement as his. The decision that superseded them was in a
companion session log, which is where this project records his choices, and I
had not looked there. **Check the session logs, not only the specs.**

### UI-015 [polish] Header actions are not right-aligned
> "the 'See all' buttons should be at the rightmost. same with 'Unlock with Pro'"

**Reported fixed on 10 August and it was not.** Aedwon looked again after that
change: *"also the See All buttons still aren't flush right"*.

**Checked, and he is right.** The header row held two flex children: the
heading, which is `Flexible` so a long one can shrink, and a `Spacer`. Flutter
divides free space between flex children, so the two **split it evenly** and the
Spacer only ever pushed the action half way. With a short heading like "Up next"
the action landed **236px short of the margin** at a 800px width.

The earlier fix removed the action's right padding, which was a real 8px, and
so moved it 8px of the 244 it needed. **The remaining 236 was the layout, not
the padding**, which is why the change looked like it had worked and had not.

**Fixed:** the `Spacer` is gone and the row uses `spaceBetween`, which gives the
leftover to the gap rather than dividing it. A test now asserts the action's
right edge meets the panel's content edge, so this cannot regress silently
again.

### UI-044 [blocker] "extP1,370.00" in the answer choices, and what was behind it

**Aedwon:** *"i was trying out a quiz and i saw that the options have
extPXXXX.XX where P is a peso sign. can you diagnose this?"*

**It is a YAML escaping bug, and it had a second bug hiding behind it.**

**The content.** Question choices are authored in YAML. Some were written in
**double quotes**, where YAML processes backslash escapes, so `"$\text{₱}1,370.00$"`
became a **tab** followed by `ext{₱}1,370.00`. `\frac` went the same way through
`\f`, a form feed. **109 tabs and 17 form feeds across 30 questions**, all in
choices, because stems are written as block scalars where backslashes are
literal.

The authors were inconsistent rather than uniformly wrong: some double-quoted
strings correctly used `\\text`. **So the repair normalises a lone backslash to
a pair inside double-quoted scalars only**, and leaves correct ones alone. The
opposite error existed too, `\\div` inside block scalars where a pair means a
line break, and that is fixed the other way.

**A sweep of all 2,376 maths expressions in the bank** found 5 that failed to
parse. It is 2 now: a piecewise function using display delimiters, and one
using `\,` before a mid-dot. **Both are recorded and neither is a peso sign.**

**Also found: one stem had an unbalanced `$`.** `$\text{₱}13/fare.` never
closed, so every delimiter after it paired with the wrong partner.

than scattered through. **Collapsing the table therefore hides exactly them**,
which is what removing them was meant to achieve, without losing the fact that
those parts have not been started. So neither deleted nor greyed: behind a door
that says what is behind it.

**"Show more" was rejected for the same reason.** It makes a student guess
whether three rows or ninety are behind it. The control reads *"Show 12 not
started"* or *"Show 20 more, 12 not started"*.

**He is right that it was out of place, and it is checkable rather than a
matter of taste:** the sections above and below both use the panel frame and
this one did not. It does now, with the panel's heading replacing the section
header so there is still one rule under the title rather than the two four
pixels apart the spec warns about.

### UI-054 The rows carry a bar now

**Aedwon:** *"there's also no progress bar like what exists in Home (the
section that leads to Progress). can you add those as well? make sure this is
presented elegantly"*

The same component Home uses for weakest areas. **A row with nothing measured
draws no bar**, because an empty bar is a figure and there is no figure, **but
its slot is still held**, which is the rule the figure columns already follow:
one blank row must not pull the columns beside it out of line.

**The expand control is ink rather than board**, because the spec says board
green appears nowhere in this table and the colour budget keeps it for primary
actions. Weight carries it instead.

**The spec is amended in place** rather than left to disagree with the code.

### UI-055 [blocker] The collapse showed blanks to a student with no scores

**Aedwon, asking rather than reporting:** *"what's the behavior if all have
scores? obviously the 'Show X not started' will reduce in numbers but does that
mean the amount of lessons being shown gets longer?"*

**The answer to his question is no**: the collapsed height is fixed at six, so
it never grows. Only the label changes, from *"Show 12 not started"* to
*"Show 20 more topics"* once nothing is unmeasured.

**But the question found a real defect.** The collapsed view took the first six
rows of the sorted table, and unmeasured rows sort last **only when measured
ones exist**. A student with nothing measured yet opened Performance on **six
blank rows**, which is precisely what collapsing was added to remove.

**Collapsed now takes the first six *measured* rows.** With none measured the
table draws no rows and one line in their place, because a table head sitting
over nothing reads as broken rather than as empty.

**A test walks every visible row in the collapsed table and fails if any of
them has no score.**

### UI-056 [important] The miss counts were a wrapping paragraph

**Aedwon:** *"please fix the presentation of the figures in Why you miss
questions. it's so awkward and not elegant at all"*

**Two things were wrong, and the spec was one of them.**

**What was built:** the three counts and their labels in a *single* `Text.rich`
paragraph, separated by middle dots. On a phone that wraps wherever it happens
to land, so a number could end a line with its label starting the next, and a
dot could dangle at a line end. That is the awkwardness.

**What the spec asked for was a ruled band**, and the band does not fit.
Measured at three widths: the three counts with these labels need about
**368px**, inside a panel that has **343 at 411dp** and less below that. A band
would always have fallen back to scrolling sideways, which is the accessibility
fallback rather than a layout.

**Shortening the labels was tried first and was not enough**, and it spends the
spec's words for nothing.

**Stacked instead, one count per line**, the numeral in a fixed right-aligned
column so a 3 and a 12 put their labels on the same vertical line. Figures stay
first, every word survives, and it fits any width.

**Two tests:** that the labels are stacked and share a left edge, and that a
320dp phone renders it without exception.

**The spec is amended** rather than left asking for a band that cannot fit.

### UI-057 [polish] The stacked counts sat against the panel's left edge

**Aedwon:** *"can you at least center them or something they look awkward being
flushed left"*

**Centred as a block, not line by line.** Centring each line on its own would
have broken the thing the stack was for: the labels are different lengths, so
the numerals would stop lining up under each other. The group is sized to its
widest line and that is centred, which keeps the numeral column and the labels
aligned inside it.

**The narrow-phone test earned its place immediately.** Removing the label's
`Expanded` to let the row shrink wrap meant the label could no longer shrink,
and a 320dp screen overflowed by 25px. It is `Flexible` now: the row still
sizes to its content, and the label still wraps when squeezed.

### UI-058 [blocker] The Go deeper subtitle invented the student's verdict

**Aedwon:** *"for the Go deeper section, the 'How you work' subtitle is already
showing data but when clicking to see the actual page it all says not enough
data yet. fix that."*

**He found a contradiction and underneath it was a printed invention.** With no
archetype and no measured hours the row printed **the design spec's own
illustrative example**, *"Night-Owl Sprinter. Sharpest at 9 pm, in 8 minute
sits."*, as though it were this student's reading. The page behind it was
telling the truth; the row was not.

**It was also the error fallback**, on both rows: a failed read printed the
same invented verdict, and Your record printed *"Day 1."*, which is equally a
figure the app had not measured.

**This is the rule in `CLAUDE.md` Section 1**, that nothing this project
inferred on its own may be printed as a figure. It had already killed a fully
designed section. Here it had shipped.

**Fixed:** nothing measured says *"Not enough data yet"*, matching the page.
Loading and error draw no subtitle at all, since an empty one is simply not
rendered.

**Two guards**, one for the empty case and one for the failed read, both
verified to fail against the old behaviour. Getting them to bite took four
attempts: the section does not render without an exam, an attempt count and a
pace reading, so the earlier versions were passing on a page that had not drawn
the row at all.
