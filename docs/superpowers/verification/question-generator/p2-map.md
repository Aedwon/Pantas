## Lead rulings (Nov 21, binding for every Phase 2 family)

Part A of the spec is unchanged by all of these. L4 changes Part B and plan Task 2.4 and is recorded in the decision log.

- L1 Wire. Accept the section 8 shapes. Variants are delivered rendered (stem, explanation, choices, figures per index); the app and server never evaluate templates. One logical record feeds both the native and the web adapter. A type joins the question set of its `lesson`. Phase 1 `index` becomes `variantIndex` at the export boundary. The Free variant document stays under 200 KB, enforced at export; record the largest real size. Pro notes are keyed by variantIndex and source-order choice position; a Free read never receives a note (test).
- L2 Active state. One policy, computed once in the logical record and applied by both adapters: type enabled means the type row is active and its merged questions inactive; disabled means the reverse. Web question-set upserts write `isActive` explicitly for these rows instead of keeping the old value on conflict. Test both directions on both adapters.
- L3 Shared code. `resolveVariant` and `chooseVariant` are pure Dart in `lib/core/storage/domain/`, with the section 8 signatures (`chooseVariant` takes `ruleKeysByIndex`). The server uses the same code through `server_dart`.
- L4 Served state is derived from answers. Its source of truth is the answer records that already sync (attempt items, mock answers, server sessions), each carrying `variantIndex`. The local review state gains `servedVariantsJson` only as a cache: updated on each submit, rebuilt from answers on migration and after a pull. The `fsrs_cards` documents gain no field, so an old client cannot drop served state. Union across devices follows from syncing the answers. Every answer source counts, whatever the scheduler state (map, answer identity). This replaces plan Task 2.4's `servedVariants` field on `fsrs_cards`.
- L5 Session pinning. The variantIndex is chosen when an item is served and pinned in the session state for that session's life, including resume and retry. It counts as served only when its answer is submitted. Session JSON stays readable in the old form; a bare type id found on resume is chosen once and then pinned.
- L6 Availability. Every serve route resolves before display. A type with no variant document, or with an index outside its list, is skipped on that route. It is never shown with empty slots.
- L7 Old clients. Content with type rows must not break a client built from current main. The Content Resolve family tests current-main client code against the new export. If an old client would show a type row, the export must carry type rows in a form old clients ignore; record what was done. Release order: app and functions first, then content with enabled types.
- L8 Server. Ingestion rejects a variantIndex outside 0 to variantCount minus 1 for a type id. Answer correctness for types uses today's contract for singles; no new correctness contract in this build. Mock papers pin the index. Rollback never deletes a variant document, so past answers still resolve.
- L9 Server JS. Keep the byte comparison of a fresh `pantas_core.js` build; extend the fixtures to any new bridge operation.
- L10 Waves. Wave 1, parallel worktrees: Export, Content Resolve, Answers and Review State. Wave 2: Selection, Sync, Server. Wave 3: Carry-over alias, List use, the free-tier count.
