## AMENDED 4 August 2026: the count is a parameter, never three

**"Three" came from `2026-07-26-home-and-navigation-design.md` and was never derived from
anything.** It is struck.
`docs/superpowers/specs/2026-08-04-study-plan-forward-calendar-design.md` Section 3 computes a
daily lesson count from the material remaining and the days left, so **the number is different
for every student and changes as their exam approaches.**

Aedwon's test, which is why a constant cannot survive: a student with ten days left has about
eight working days, and three lessons a day would cover twenty four lessons of a far larger
corpus. **A fixed daily number makes the plan's own promise impossible to keep.**

**What changes in this plan:**

1. **The provider answers "which lessons today", not "which three lessons".** It takes the count
   from the plan and returns that many.
2. **Its lead sentence must survive N of 1 and N of 12.** Write it to pluralize and to read
   sensibly at both ends, and test both.
3. **The panel still opens one lesson per row**, unchanged. The start index this plan reserved
   is now filled by the plan's ordering rather than left waiting.
4. **Nothing here computes the count.** If the study plan is unavailable, fall back to the
   panel's existing behavior rather than inventing a number.

**Everything else in this plan stands.**

## The chain is not built here, and this is why

> **SUPERSEDED 4 August 2026 by the amendment at the top of this plan.** The reasoning below
> was correct when the study plan's providers threw. They no longer do, the plan computes a
> daily lesson count, and the reader's counter now renders "2 of N". Kept because it records
> why the omission was a decision rather than an oversight.

The 26 July spec says "Continue lesson" resolves the day into three lesson ids, passes
them to the reader as route arguments, and pays for a "2 of 3" counter, boundary ticks and
pull-to-advance.

**The reader cannot draw that counter.** Study Plan 4 built the reader's Study composition
only and deliberately reserved the second value, because the study-plan feature's providers
throw: `/plan` is unlinked, UI-003 is open, and the entry row was hidden on 25 July.
Passing a three-lesson chain into a reader that has nowhere to show a position would
produce a silent no-op, and a student who tapped row two would land in the reader's no-plan
mode without being told.

**So a row opens its own lesson and nothing more.** When the study plan becomes real, the
chain drops into the shape Study Plan 4 reserved, and this panel gains a start index
without changing its composition. Recorded here so the omission reads as a decision.

**One thing this does not get to degrade on.** The Study spec's day line, "That's enough
for today.", depends on Home still making a real offer, or the app is sending someone to
bed with nothing to do. That is why the finish state below states the work rather than
going quiet.

  /// an empty list caused by having no topics or no content.

}

final upNextProvider = FutureProvider<UpNextDay>(...);

**The selection rule, in order:**

1. Rank the exam's topics by accuracy ascending, over `attempts_local` items joined to
   their questions' `topicId`, exactly as Plan 5's panel ranks them. Same source, so the
   two panels can never name a topic weak in one and strong in the other.
2. Walk that ranking from the weakest. From each topic take its unread lessons in
   `ordering` (glob order until Study Plan 1's column lands).
3. Stop at the day's lesson count, which the study plan supplies. Never a constant.
4. If the ranking is exhausted before three, return what there is with
   `allReadInWeakTopics: true` when every weak topic was fully read, and `false` when the
   shortfall is because there is no content.

**Unread means no `lesson_progress_local` row.** That table's primary key is `lessonId`
and its only other column is `readAt`, so presence is the whole test.

**Three from three topics is not required.** The spec's example names three subjects, but
taking two from Algebra when Algebra is much the weakest is the correct behavior and the
spec never says otherwise. The lead sentence names the distinct subjects it actually got.

**after** measured ones.

- [ ] **Step 3: Write the panel**

The sentence builder is the fiddly part, so give it its own tested function:

```dart
/// "Algebra, Geometry and Chemistry today. About 28 minutes."
///
/// "About" is the content's hedge, not the app's: estimatedMinutes is an
/// authored field. Elsewhere on Home the app states figures it knows
/// exactly and does not hedge them.
@visibleForTesting
String leadSentence(List<UpNextLesson> lessons) {
  final subjects = <String>[];
  for (final lesson in lessons) {
    if (!subjects.contains(lesson.subjectName)) subjects.add(lesson.subjectName);
  }
  final minutes = lessons.fold<int>(0, (sum, l) => sum + l.estimatedMinutes);
  final unit = minutes == 1 ? 'minute' : 'minutes';
  return '${_join(subjects)} today. About $minutes $unit.';
}

String _join(List<String> parts) {
  if (parts.length == 1) return parts.single;
  return '${parts.sublist(0, parts.length - 1).join(', ')} and ${parts.last}';
}
```
