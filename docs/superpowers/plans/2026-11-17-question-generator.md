# Question generator implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. In this repository `WORKFLOW.md` wins where a skill differs: no human checkpoints, the lead commits, full code in every step is not required.

**Goal:** problem types whose checked versions replace near-duplicate questions, abstract reasoning first, then a CSE math pilot, with app and server support that serves an unused version each time.

**Architecture:** an offline Dart generator writes a fixed list of versions per problem type; an independent checker proves every version. The app and server treat a problem type as one question id and resolve (id, variant index) to a normal question before any screen or scheduler sees it. Only the answer record and the review state learn about variants.

**Tech stack:** Dart 3 (tool and app), Flutter, drift, freezed, Firebase Cloud Functions (TypeScript plus app Dart compiled to JS in `server_dart/`), Firestore.

**Controlling documents:** spec `docs/superpowers/specs/2026-11-17-question-generator-design.md` (Part A approved Nov 17), decision log `docs/superpowers/decisions/2026-11-17-question-generator-log.md`. Policy read at `origin/main` 12fde7532. Velocity rows E-107 (plan) and E-109 to E-112 (build).

## Part 3: formats (interfaces every task shares)

Naming: the yaml field `type` already means question format (`figure-series`, `word-problem`). A problem type is called a **problem type** in docs and `ProblemType` in code. Its id prefix is `qt-`.

Problem type file, `content/types/<subject>/<topic>/<lesson-slug>/<qt-id>.yaml`:

```yaml
id: qt-spatial-abstract-reasoning-turn-step
lesson: lesson-spatial-abstract-reasoning-figure-turns-and-positions
keyPoint: 1
difficulty: easy
exams: [acet, ustet, dost-sei, cse-pro]
format: figure-series          # the existing question `type`, copied to exported rows
rule: figureSeriesTurnStep     # class in tool/generator/rules/
ruleVersion: 1
choiceCount: 4
choiceKind: figure             # figure (figure data plus text) or text (text only); same for every choice of the type
enabled: true                  # false = rollback: type inactive, merged questions active
params: { stepDegrees: [45, 90], length: [3, 4], forms: [square, circle] }
stem: "Which figure best continues the simplest consistent pattern shown?"
explanation: "The line turns {dir} by {step} degrees each time. One more equal step points {answerText}."
mistakes:
  - id: double-turn
    note: "This doubles the last turn to {wrongStep} degrees. ... Check the equal steps already shown."
mergedQuestions:               # hand-written questions that become versions, fixed indexes
  - { id: q-spatial-abstract-reasoning-figure-series-0001, index: 0 }
```

Variant list, next to it as `<qt-id>.variants.yaml` (data, committed, appended on refill, never reindexed):

```yaml
problemType: qt-spatial-abstract-reasoning-turn-step
generator: { tool: 1, ruleVersion: 1, seed: 20261117 }
variants:
  - index: 0
    source: q-spatial-abstract-reasoning-figure-series-0001   # only for merged questions
    slots: { dir: clockwise, step: 45, answerText: lower-right }
    figureSpec: { kind: figure-series, items: [...], blank: true }  # figure types only
    choices:                        # stored order is display order
      - { correct: true, text: "Line pointing lower-right", figure: {...} }
      - { mistake: double-turn, text: "Line pointing down", figure: {...}, slots: { wrongStep: 90 } }
    ruleKey: <sha256 of the rule-parameter set only>             # cosmetic attributes excluded
    cosmetics: { form: circle, fill: white }                     # attributes the rule ignores, constant across the whole version
    signature: <sha256 of the canonical figure or number set>
```

Math variants use `value` (exact rational as `"p/q"` or integer string) on each choice and render `text` from the type's choice template; `figure` is absent.

Exported to the app (Phase 2): one question row per problem type (id `qt-...`, `isActive` from `enabled`, `variantCount`) inside its lesson's question set, and one variant document per problem type, `content/variants/{qtId}` (Free part: stem, choices, explanation slots and figures; Pro part: note slots and templates, in the existing Pro document path). The old-id map is the `mergedQuestions` list on the row.

Dart interfaces (tool, Phase 1; reused by the app in Phase 2 where marked):

- `ProblemType` and `Variant` value classes, `parseProblemType(Map) -> ProblemType`, `parseVariants(Map) -> List<Variant>` in `tool/generator/lib/src/model.dart`. The app copies only the parse and resolve code it needs into `lib/` (no import from `tool/`).
- `abstract class Rule { String get name; int get version; Variant generate(ProblemType t, Random r, int index); }` and `ruleRegistry: Map<String, Rule>` in `tool/generator/lib/src/rules/`.
- `abstract class FigureSolver { bool fits(FigureSpec shown, FigureSpec candidate); }` per rule, in `tool/generator/lib/src/check/solvers/`, sharing no code with `rules/` beyond the model.
- `resolveVariant(Question typeRow, VariantDoc doc, int index) -> Question` (app, Phase 2): fills slots, returns an ordinary `Question` whose id is the type id.
- `chooseVariant({required String uid, required String typeId, required int count, required Map<int, DateTime> served}) -> int` (app and server Dart, Phase 2): seeded permutation of `0..count-1` by `sha256(uid + typeId)`; first index not in `served` whose `ruleKey` is not yet served (Fable ruling 2b), then any unserved index; if none, the index with the oldest served time.

## Part 3b: adviser rulings, Nov 16 (Fable 5.2; record on main in the decision log)

These apply before the affected code changes.

1. A one-question pattern becomes a problem type with that question at index 0 when the rule reproduces it exactly; otherwise it stays a single. Types are not limited to merge groups. Build types in descending capacity order.
2. Lists under 100 go to Aedwon (Part A says "Start size: 100 versions per type"). Until he answers: build the generator, the checker and every type that enumerates to 100 or more; hold shipping any list under 100 and any under-20 cut-off. Widening with attributes the rule ignores is allowed only if (a) the attribute is constant across every figure in one version, shown figures and choices, and varies only between versions; (b) each variant records its rule-parameter set (`ruleKey`) apart from its cosmetics, and the serve order cycles through distinct `ruleKey`s before it reuses one; (c) each type reports two enumerated numbers, distinct rule-parameter sets and total versions (generate, then dedupe by signature), never estimates. All paper-fold candidates and the no-figure questions stay singles. The fold painter is not touched.
3. The cube-net signature ignores label permutations. Labels may be shuffled between versions as a cosmetic; that adds no capacity.
4. Each type declares `choiceKind`: `figure` (figure data plus text) or `text` (a count, a condition, an order or a relation). All choices in one question use the same kind. Singles with undrawable answer figures (series 0002, 0005, 0007, 0008; matrices 0002) keep text choices. The figure-choice UI lead is told.
5. A type whose index 0 differs from its live source question does not ship. Series 0019's wrong-choice note (says 90 degrees; the choice is a 135-degree overshoot) is fixed in the source question through the content approval gate first; the type names the 135-degree mistake.

The checker gains: `ruleKey` recomputed independently by the solver and compared; cosmetics constant across the version; `choiceKind: text` choices carry no figure; the capacity report (`bin/capacity.dart`: distinct `ruleKey`s and total signatures per type at a given ceiling).

Checks, for every variant of every problem type (spec B5):

1. Exactly one correct choice by a second solver that imports nothing from `rules/`. Math: evaluate the type's formula from `slots` with exact rationals.
