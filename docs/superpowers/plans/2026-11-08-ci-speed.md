## For Aedwon (approval section)

**Status.** Approved by Aedwon, Nov 10, 2026. Nothing is built.

**Close-out, Nov 11, 2026.** Goal met on `web/design-system-4`. A code-only push now takes a
median of 3 min 33 s (213 s), from 28.5 min at the start of Nov 10. Same tests by name, coverage
92.4% throughout. Two items wait for main's freeze to lift; see "Close-out" at the end.

**Why.** A push now takes about 30 minutes to get a pass or fail. It took 26 minutes on Nov 8.
The slowest test group runs 27.5 of its 40 allowed minutes. At this growth, groups could reach
the limit within weeks.

**Goal.** Same checks and the same coverage gate on every run, but faster.
- Steps 1 to 4 bring a push to about 5.5 to 7 minutes.
- Step 5 brings it to about 4 to 5 minutes.
- Under 4 minutes needs paid runners or fewer tests. I do not advise either.

**Steps, ranked by gain for the work.** All are free.
1. Split the tests by file into 8 groups. Saves about 21 to 23 minutes. Work: half a day to a day.
   Low risk.
2. Run the Android build only on main, before a release, and when Android files change.
   Saves 2 to 3 minutes. Work: 1 to 2 hours. Cost: a break that only affects Android shows up on
   main, not on the branch. You need to accept this.
3. Make setup faster in every job, and make the coverage job lighter. Saves 1 to 1.5 minutes.
   Work: 2 to 4 hours.
4. Stop the duplicate run when one commit sits on both a `ds4/` and a `web/` branch. Cut the
   number of jobs. Saves 0 to 2 minutes of waiting and halves the compute. Work: 30 minutes.
5. Fix the slowest tests. Then bundle small sets of test files and use 12 groups, only if still
   over the target. Saves 1 to 1.5 minutes. Work: 1 to 1.5 days. Bundling has medium risk, because
   one test file can leak state into another.

**Time and timing.**
- Steps 1 to 4: about 1.5 days. With step 5: about 3 days.
- Work starts right after the design system 4.0 redesign ships to prod.
- It starts before the post-ship merges: guardrails, completion, privacy batch, custom exams.
  Those merges then land on the faster CI.

**Main risk.** A check could silently run fewer tests. Every step proves that the same tests ran,
by name, and that coverage is the same, before it lands.

**Not changing.** Which checks must pass, the coverage gate (70%), the attribution and secret
scans, and the browser journeys (they are fixed separately).

**Done means.** Ten pushes in a row have a median under 7 minutes after steps 1 to 4, with the
same test count measured at the start, and coverage within 0.5 points of the start. If step 5 is
built, the median is under 5 minutes.

**Your decisions.** Approve the plan. Accept the Android change in step 2.

### Steps

**S0. Baseline harness and re-baseline.** Add `tool/ci/test_timing.dart`, which runs
`flutter test --reporter json` on a file list and writes per-file load and run time. Add a
workflow_dispatch job that runs the full suite unsharded with the JSON reporter and uploads the
timing file as an artifact. Run it on the branch that has shipped to prod at the start. Record:
test count and test identities (suite path plus test name), per-file time, covered lines and the
line total, coverage percent, `.dart_tool/build` size, and the cold build_runner time. Pin the
"done" test count to this measurement. Also measure `-j 2, 4, 6, 8` on identical file sets.

**S1. File-based shards, 8 groups.** Replace `--total-shards/--shard-index` with an explicit file
list per shard. `tool/ci/shard_tests.dart`:
- lists `test/**/*_test.dart` and excludes `test/goldens/**` (they run in the goldens job; today
  they load and skip in every shard);
- reads `tool/ci/test_timings.json` (checked in, from S0); unknown files get the median time;
- assigns files to 8 shards by longest-processing-time first (greedy, deterministic);
- prints the list for shard K; the job runs `flutter test --coverage <files...>`.
A check job verifies that the union of shard lists equals the full file list minus
`test/goldens/**` (none dropped, none twice).
Timing file upkeep: 160 files arrived in two days, so a hand-refreshed file goes stale. Each
main run uploads a timing artifact from its shards (`--file-reporter json`). A weekly scheduled
job merges them into a proposed `test_timings.json`. The shard job prints the slowest shard
against the mean; when the slowest is more than 20% over the mean, the lead commits the refreshed
file.
After S1 lands, lower the test timeout from 40 to about 15 min so a hung shard fails fast.
Expected (Fable estimate): slowest shard about 7 min. Verify on CI before merging: the same test
identities and outcomes as S0; coverage lines and line total within 0.5 points.

**S1b. Android build cache.** Add `gradle/actions/setup-gradle` (pinned by SHA) with the Gradle
build cache on (`org.gradle.caching=true` in `android/gradle.properties`). Expected 1 to 3
minutes off the Android job (521 s today), for the runs that still build Android. Verify a cold
build still passes.

**S2. Shard count and job count.**
- Benchmark `flutter test -j` values from S0 on the 8 file shards (compilation is serialized, so
  more may be slower).
- Start at 8 shards (S1). Move to 12 only if S5 leaves the median over target. The 20-job limit is
  account-wide, not per workflow: agent sessions push different branches at the same time, and
  two overlapping runs of 16 jobs exceed it and queue.
- Cut the job count: gitleaks, semgrep and the attribution scan move into one `scans` job with
  no app setup (so a bad commit fails in about a minute); the OSV report moves to a schedule plus
  runs on a change to `pubspec.lock` or `functions/package-lock.json`. Target: 16 jobs or fewer
  per run with 8 shards, including `ci-ok`.

**S3. Incremental setup, one saver per cache.** Replaces the Nov 8 "skip generation on a hit"
design, which would almost never hit (the key hashed `lib/**`, and every job in a run starts
together, so none can reuse another's save).
- build_runner: restore `.dart_tool/build` with a prefix key (flutter version, OS, `pubspec.lock`,
  `build.yaml`) and `restore-keys`, then always run build_runner. It checks its own inputs by
  content and rebuilds only what changed, so stale output is not possible. A new key per commit
  (suffix the SHA) lets the saver refresh it. Before relying on it, S0 proves that a restore into
  a fresh checkout regenerates every output file with identical bytes to a cold build, including
  `.g.dart` files that are absent from the checkout.
- Content asset (`build/export.json`, `assets/seed`): its own key from the content sources and
  `tools/**`, not `lib/**`. Only that key, so it hits on most code pushes. After a restore, still
  run the `touch` of the manifest files. S0 compares the restored bytes against a cold build.
- Setup retry: retry `setup-app` once on failure (the profile saw setup flakes cost 100 to
  217 s).
- Coverage job: drop the Flutter install and `pub get`. Run `check_coverage.dart` with the Dart
  SDK alone (`dart-lang/setup-dart` pinned by SHA, version taken from Flutter 3.44.6, or a shell
  gate); it imports only `dart:io`. Expected 20 to 30 s off every run (Fable estimate).
- Cross-branch rule (E5): a branch reads only its own caches and main's. Main runs a different
  workflow today, so nothing seeds a new `web/**` branch. One job saves each cache
  (`actions/cache/save`), every other job only restores (`actions/cache/restore`), and main runs
  the same setup (S4) so it seeds the cache. Watch the size: the repository is already at 11.3 GB
  of caches. Record each cache's size; do not add a cache that evicts the 1.6 GB Flutter cache.
- Test compiler cache (`build/test_cache`): measure once; keep it only if it saves over 30 s
  per shard on a cold start.
- Cache the Firebase emulator jars (`~/.cache/firebase/emulators`) and the Playwright browser.
- The 1.6 GB Flutter cache restore costs only 17 s; leave it.
Expected (Fable estimate): setup falls from about 100 s to about 45 to 60 s in every job; the
coverage trim adds 20 to 30 s. Both are estimates until S3 measures them.

**S4. No duplicate runs, and what main runs today.**
Verified at `origin/main` 2651a6fd0 and `origin/ds4/completion-r1` d2ee9927c:
- Main today: `ci.yml` ("CI (PR)") runs on pull requests into main only, as one unsharded job on
  Flutter 3.41.x with a 15 min limit (plus `sast` and `osv`). `main.yml` ("CI (main)") runs on
  push to main, one job on Flutter 3.41.x with a 30 min limit, and also builds the debug APK and
  uploads it as the `app-dev-debug` artifact.
- The sharded `ci.yml` on Flutter 3.44.6 exists only on the redesign branches. It runs on pull
  requests into main and on pushes to `main`, `web/**` and `ds4/**` (not
  `web/staging-candidate-r1`). `main.yml` is unchanged there, so once this `ci.yml` reaches main,
  `main.yml` and `ci.yml` would both run on every push to main.
Changes, in one change set:
- Land the sharded `ci.yml` on main and delete `main.yml`. Decide whether anyone uses the
  `app-dev-debug` artifact; if so, upload it from the Android job on main.
- Branch protection: none exists, so no name needs updating. Require only `ci-ok` if protection is
  ever added.
- Twin branches: `ds4/completion-r1` and `web/ds4-completion-r1` point at the same commit
  (d2ee9927c). Both match the push trigger, so one push started two full CI runs (42766775030 and
  42766777536, created one second apart, finished 06:41 and 06:43). The concurrency group is per
  branch, so they never cancel each other. Fix at the trigger: stop pushing the twin name, or list
  one branch family for pushes. A guard job that compares runs is racy (the runs start one second
  apart), so it is not used. The lead picks the rule with the manager's branch convention.
- A pull request from a `web/**` branch fires CI twice (pull_request plus push, different
  concurrency groups). Keep the pull_request run (it tests the merge commit) and skip the push run
  when an open PR exists, or accept the duplicate. Do not cancel by head SHA: the PR run tests a
  different SHA.
- Browser journeys run once per push on `web/**` only; leave them.

**S5. Slow tests.**
- local_onboarding_presets (86 s; one test 40 s in a `runAsync` loop over 19 presets): split per
  preset or run presets in parallel; keep every assertion.
- read_marking dwell floor (16 s real `Future.delayed`): drive the clock with `fakeAsync` or an
  injectable clock.
- Content-export `setUpAll` blocks (cse_blueprint, upcat_blueprint, upcat_end_to_end,
  topic_prerequisites and others): point the tests at the `build/export.json` that `setup-app`
  already builds in every job (S3 adds no `prepare` job), through an environment variable; fall
  back to building locally when unset.
- production_sync_runtime_engine backoff (7.5 s real delays): inject the delay.
- Re-profile after each; stop when no file is over 20 s. These timings are from Nov 8; re-run S0
  before choosing targets.

**S6. Run only what changed, on branches.** Use a path filter job (`dorny/paths-filter` pinned by
SHA, or a small `git diff` script):
- Flutter tests, static, web: when `lib/**`, `test/**`, `pubspec.*`, `build.yaml`, `l10n.yaml`,
  `tool/**`, `tools/**`, `content/**`, `assets/**`, `web/**` or workflows change.
- functions: when `functions/**`, `content/exams/catalog.json` (its build reads it),
  `firestore.rules`, `storage.rules`, `firebase.json` or workflows change.
- android: only on main, on release (release tags and workflow_dispatch), and when `android/**`
  or `pubspec.*` change. It does not run on `lib/**` alone: the VM tests already compile `lib/`.
  The old rule ran Android on `lib/**`, which is almost every push, so it saved nothing and kept
  Android (8.7 min) as the slowest job. Accepted cost: an Android-only break shows on main, not on
  the branch (Aedwon's decision, listed in the approval section).
- No usable base commit (a new branch, a force-push, or an all-zero "before" SHA): run everything.
A final `ci-ok` job runs with `if: always()`, `needs` all jobs, and passes only when each passed
or was skipped by the filter; a failed, cancelled or unexpectedly skipped job (coverage included)
fails it. Always run everything on main, on release tags and on workflow_dispatch.

**S7. Functions job.** Cache the emulator jars (about 10 s) and split the 37 emulator files across
two jobs (30 to 60 s; separate runners avoid fixture collisions). Off the critical path
(120 s today), so do it last.

Coverage stays on every required run (removing it on branches weakens verification). Measure its
overhead for the record only.

**S8. Bundled tests, 12 groups (later, only if needed).** Only if steps 1 to 4 and S5 leave the
median over the target (under 7 minutes; under 5 if the 4 to 5 minute goal stands). Move to 12
shards (S2) and try several small bundles per shard, with `very_good test --optimization` or
generated bundle files, on a branch. Keep outside the bundle: the 20 files that start processes,
release_e2e_runner, and files that set global state (debugDefaultTargetPlatformOverride 3,
FlutterError.onError 2, HttpOverrides 1, method-channel mocks 11) unless each resets in tearDown.
Accept only with the same test count and no new flakes over 10 runs. Medium risk.

- Every shard uploads a fresh coverage file; compare covered lines and the line total, not only

- Platform annotations keep their meaning (the browser-only database test still skips on VM).
- Ten consecutive CI runs: record wall median and the slowest job.
- A cached step (S3) must give the same generated output as a cold one.
- `ci-ok` is the one name to require if branch protection is added.

### Ideas considered and not taken (Fable, with reasons)

- Affected-test selection as the required gate: generated code, assets and content make the
  dependency graph incomplete, and the coverage gate needs the full suite.
- Merge queue with a fast gate: GitHub offers it for organization-owned repositories only (not
  re-verified); a hand-built two-tier gate would break the rule that staging only takes a commit
  that passed the full run.
- Larger GitHub runners, third-party runners: paid or a new vendor with access to the build; free
  shards give the same result.
- Self-hosted Mac runners for required checks: a pull request on a public repository can run code
  on the Mac, which is shared with agent sessions and sleeps.
- Prebuilt Flutter container image: the image pull is slower than the 17 s cache restore.
- Optional, not in scope: a not-required fast job that runs only the test files changed in the
  push (2 to 3 hours; shows a failure in new tests in about 2 to 3 minutes). Reconsider if agents
  wait on red runs often.
