# CI speed plan

Date: November 8, 2026. Status: ready, for after the beta. Reviewed by Codex 6.1 Sol High (high effort) on Nov 8; its corrections are folded in (Aedwon: "the implementation of this
can be after beta, just have the plan fully ready").

## For Aedwon (approval section)

**Today.** A push takes about 26 minutes before CI says pass or fail. Almost all of it is the
Flutter test step. The tests are split into 6 parallel groups, but the split is by individual
test, not by test file, so every group still prepares all 1,033 test files. Preparing files is
about 70% of test time. We pay it 6 times.

**Goal.** About 6 to 9 minutes per push, with the same checks and the same coverage gate on every
run. 5 minutes is a stretch, not a promise: the Android build alone takes about 8 minutes today
and must be sped up too. A reviewer (Codex 6.1 Sol High) checked this plan and gave the same range.

**What changes, in order:**

1. Split the tests by file, balanced by how long each file takes. Each group prepares about a
   sixth of the files instead of all of them. Biggest single gain, low risk.
2. Speed up the Android build by keeping its build cache between runs (1 to 3 minutes saved).
   After step 1 it becomes the slowest job.
3. Tune how many test files run at once on each machine, and use more groups (8 to 12). Free on
   this public repository.
4. Stop redoing the same generated code and content file in every job, and keep the compiler's
   work between runs.
5. Stop duplicate runs: one CI run per push, not two (main and pull requests currently run twice).
6. Speed up the slowest tests (one takes 86 seconds) and the tests that rebuild content files.
7. Run the Android build and the server tests only when their code changed; always on main and
   before any release.
8. Optional, only if still over 8 minutes: bundle small sets of test files together. Medium risk.

**Cost and risk.** No money: standard runners are free here. About 1.5 to 2 days of work.
The main risk is a check silently running fewer tests; every step proves the same tests ran (by
name, not just by count) and the same coverage before it lands. Branch protection names change, so the required-check
list on GitHub must be updated in the same change.

**Not changing.** Which checks must pass, the coverage gate (70%), the attribution and secret
scans, and the browser journeys (they are fixed separately).

**Done means.** Ten pushes in a row have a median under 9 minutes (stretch 6), the same test count as
today (8,210 at the time of writing, or more), and coverage within 0.5 points of today.

## Agent section

### Measured baseline (read-only profile, branch `web/web-hidden-r1` at 207010be8)

- CI (PR) wall median 26m16s over 10 runs (22m37s to 27m31s). Queue 1 to 3 s.
- Critical path: slowest test shard, step median 1244 s (933 to 1447). Shard spread up to 440 s.
- `setup-app` median 108 s: build_runner about 52 s (4,149 outputs), Flutter cache restore
  17 s (1.6 GB), content asset about 6 s. Runs 9 times per push in CI plus once in journeys.
- `flutter test --total-shards 6` loads all 1,033 suites in every shard (shard 0 loaded 1,033
  suites and ran 1,522 of 8,210 tests). Local full suite: 874 s wall on 10 cores; suite loading
  47.9 min summed vs 21.2 min of test bodies.
- Other jobs: android 394 s build plus setup; functions 132 s (emulator phase 111 s, serial,
  emulator jar downloaded every run); web build 58 s; analyze 30 s.
- Slowest files: local_onboarding_presets 86 s; release_e2e_runner 43 s;
  build_content_export_links 35 s; web_quiz_live 33 s; bookmarks_sheet 30 s.
  Several `setUpAll` blocks spawn `dart run` content exports (7 to 12 s each).
- Duplicates: `main.yml` repeats `ci.yml` on push to main (unsharded, Flutter 3.41.x pinned
  instead of 3.44.6). A pull request from a `web/**` branch runs CI twice.
- Unmeasured: coverage overhead, `-j` effect on 4 vCPU, very_good bundling.

### Steps

Each step lands alone with before and after numbers recorded in the log.

**S0. Baseline harness.** Add a script `tool/ci/test_timing.dart` that runs
`flutter test --reporter json` on a file list and writes per-file load and run time. Add a
workflow_dispatch job that runs the full suite unsharded with the JSON reporter and uploads the
timing file as an artifact. Record: test count, per-file time, coverage percent.

**S1. File-based shards.** Replace `--total-shards/--shard-index` with an explicit file list per
shard. `tool/ci/shard_tests.dart`:
- lists `test/**/*_test.dart`;
- reads `tool/ci/test_timings.json` (checked in, from S0; refreshed by hand or a monthly job);
  unknown files get the median time;
- assigns files to N shards by longest-processing-time first (greedy, deterministic);
- prints the list for shard K; the job runs `flutter test --coverage <files...>`.
A check job verifies the union of shard lists equals the full file list (no file dropped, none
twice). Expected: per-shard load cost falls about N-fold. Verify on CI before merging: total
test count equals S0; coverage within 0.5 points.

**S1b. Android build cache (reviewer).** Add `gradle/actions/setup-gradle` (pinned by SHA) with
the Gradle build cache on (`org.gradle.caching=true` in `android/gradle.properties`). Expected 1 to
3 minutes off the Android job, which becomes the critical path after S1 (today about 8m22s with
setup). Verify a cold build still passes.

**S2. Test concurrency and shard count.** First benchmark `flutter test -j 2, 4, 6, 8` with
coverage on identical file shards (compilation is serialized, so more may be slower). Then With S1 in place, measure N = 6, 8, 10, 12 (workflow_dispatch matrix).
Pick the smallest N where the slowest shard plus setup is under 5 minutes. Hosted runners are
free for public repositories. The 20-job limit is account-wide, not per workflow: count browser
journeys and overlapping runs, so keep one run under about 16 jobs.

**S3. One setup, reused.**
- Cache the build_runner, gen-l10n and content-asset outputs with `actions/cache`, keyed by the
  Flutter version, OS, `pubspec.lock`, `build.yaml`, l10n config, and hashes of `lib/**`,
  `tools/**`, `tool/**` and content sources. On a hit every job skips generation; on a miss each
  job generates as today. Do not add a `prepare` job that others wait on: the reviewer noted the
  barrier can cost the wall time it saves. Benchmark both if unsure.
- Restore Flutter's incremental test compiler cache (`build/test_cache`) keyed by SDK, OS and
  `pubspec.lock`. Flutter still recompiles changed sources; this only seeds the compiler. 0 to
  60 s per shard.
- Cache the Firebase emulator jars (`~/.cache/firebase/emulators`) and the Playwright browser.
- The 1.6 GB Flutter cache restore costs only 17 s; leave it.
Expected: 40 to 60 s saved per job on a cache hit.

**S4. No duplicate runs.**
- Delete `main.yml`; `ci.yml` already runs on push to main, sharded, on Flutter 3.44.6 (main.yml
  pins 3.41.x). If kept, it must lose its push trigger, or both will run. Branch protection must
  name the new checks.
- For pull requests from `web/**` branches, keep the pull_request run (it tests the merge
  commit) and skip the push run when an open PR exists, or accept the duplicate. Do not cancel by
  head SHA: the PR run tests a different SHA.
- Move gitleaks, semgrep and the attribution scan into a job without app setup, so a bad commit
  fails in about a minute.

**S5. Slow tests.**
- local_onboarding_presets (86 s; one test 40 s in a `runAsync` loop over 19 presets): split per
  preset or run presets in parallel; keep every assertion.
- read_marking dwell floor (16 s real `Future.delayed`): drive the clock with `fakeAsync` or an
  injectable clock.
- Content-export `setUpAll` blocks (cse_blueprint, upcat_blueprint, upcat_end_to_end,
  topic_prerequisites and others): build the export once in `prepare` (S3) and point the tests at
  it through an environment variable; fall back to building locally when unset.
- production_sync_runtime_engine backoff (7.5 s real delays): inject the delay.
- Re-profile after each; stop when no file is over 20 s.

**S6. Run only what changed, on branches.** Use a path filter job (`dorny/paths-filter` pinned
by SHA, or a small `git diff` script):
- Flutter tests, static, web: when `lib/**`, `test/**`, `pubspec.*`, `build.yaml`, `l10n.yaml`,
  `tool/**`, `tools/**`, `content/**`, `assets/**`, `web/**` or workflows change.
- functions: when `functions/**`, `content/exams/catalog.json` (its build reads it),
  `firestore.rules`, `storage.rules`, `firebase.json` or workflows change.
- android: when `android/**`, `pubspec.*` or `lib/**` change, and always on main.
A final `ci-ok` job runs with `if: always()`, `needs` all jobs, and passes only when each passed
or was skipped by the filter; a failed, cancelled or unexpectedly skipped job (coverage
included) fails it; branch protection requires only `ci-ok`. Always run everything on main, on release tags
and on workflow_dispatch.

**S7. Functions job.** Cache the emulator jars (`~/.cache/firebase/emulators`, about 10 s) and
split the 37 emulator files across two jobs (30 to 60 s; separate runners avoid fixture
collisions). Off the critical path today, so do it last.

Coverage stays on every required run (reviewer: removing it on branches weakens verification).
Measure its overhead for the record only.

**S8 (optional). Bundled tests.** Only if S1 to S7 leave the median over 8 minutes. Try several
small bundles per shard rather than one (reviewer), with `very_good test --optimization` or
generated bundle files, on a branch.
Keep outside the bundle: the 20 files that start processes, release_e2e_runner, and files that
set global state (debugDefaultTargetPlatformOverride 3, FlutterError.onError 2, HttpOverrides 1,
method-channel mocks 11) unless each resets in tearDown. Accept only with the same test count and
no new flakes over 10 runs.

### Verification for every step

- Same-commit comparison of test identities (suite path plus test name), outcomes and skips
  against S0, not only the count. Reject an empty shard. Check the shard lists partition the file
  list exactly (no file dropped, none twice).
- Every shard uploads a fresh coverage file; compare covered lines and the line total, not only
  the percent (within 0.5 points).
- Platform annotations keep their meaning (the browser-only database test still skips on VM).
- Ten consecutive CI runs: record wall median and the slowest job.
- No new required check is left unnamed in branch protection.

### Expected wall time by stage (reviewer's estimates, unmeasured)

| After | Wall time |
|---|---|
| S0 baseline, duplicates removed | about 26 min |
| S1 file shards (6) | 8.5 to 11 min |
| S1b Gradle cache, S2 concurrency tuned | 6 to 9 min |
| S2 8 to 12 shards, S3 caches | 5 to 8 min warm, 8 to 10 cold |
| S5 slow tests, S8 if needed | 5 to 7 min plausible |

### Out of scope

Fixing the browser-journeys failures (6 of 9 recent runs failed, hidden by continue-on-error),
the OSV report that always fails, and the Android build's sqlite3 download flake. Each is listed
for its own task.
