# Opus audit: Pantas web load speed (571eea1aa), written as found

## F1. The splash covers the whole Dart bootstrap plus the full Home data load; the Home skeletons already exist but are never seen on return visits
- Where: web/pantas_splash.js:8-12, 80-93; lib/app/bootstrap.dart:353 (`sendAppStarted()` just before `runApp`); lib/features/home/presentation/home_today_screen.dart:427 (`firstScreenReady(ready: done && !holding)`), :435-437 (`HomeWebLoading(more: true)` / `HomeTodaySkeleton()` already built as the not-done branch).
- What happens now: the logo stays from HTML paint through (a) main.dart.js download+parse, (b) every awaited bootstrap step (Firebase, App Check, storage, content mirror restore, Remote Config, auth, RevenueCat, sync, gates), (c) Home's entire loader (plan callable + question hydration + lesson meta + canAdvance + settings). The 8 s `GIVE_UP_MS` only starts at `sendAppStarted`, so the true cap is bootstrap time + 8 s. The skeleton branch renders under the splash and is then thrown away.
- Change (two levels): (1) no-design-change: none possible here, this is a perceived-speed lever only. (2) needs board: call `ready()` when Home's first frame with the skeleton is drawn (i.e. drop the `done` condition for Home only, keep it for error/holding), so the logo fades into the existing skeleton as soon as runApp's first route paints. Keep the 4P-2 rule (no entrance animation replay) because the skeleton has no entrance.
- Gain: ESTIMATED 1-4 s of perceived wait removed on return visits (the whole Home data phase: cold `getRoadmap` 2-5.4 s per Nov 6 logs, warm 0.07-0.3 s plus hydration). Zero gain to real time-to-usable.
- Cost on Blaze: none.
- Security impact: none.
- Risk and effort: 0.5 h code + test update; beta-safe yes; needs board YES (student sees skeleton instead of logo for the data phase).

## F3. Every `no-cache` file misses the Manila CDN edge on every request; `s-maxage` lets the edge hold them until the next deploy without any staleness for browsers
- Where: firebase.json:54-104 (`/index.html`, `/*.js`, `/` set to `no-cache`). Hosting purges its CDN on every release, so edge caching cannot outlive a deploy.
- What happens now (MEASURED, curl from Manila, Nov 7 16:43 PHT): every `no-cache` file returns `x-cache: MISS` on repeat requests (index.html, main.dart.js, flutter_bootstrap.js, drift_worker.js, part files). Files with `max-age=3600` return `x-cache: HIT`. TTFB incl. ~70 ms TCP+TLS: HIT files 0.10-0.13 s steady; MISS files 0.145-0.18 s steady with tails of 0.35, 0.73 and 0.88 s in 12 samples.
- Change: for the `no-cache` rules add the edge directive: `Cache-Control: no-cache, s-maxage=31536000` is contradictory, so use `public, max-age=0, must-revalidate, s-maxage=31536000`. Browsers still revalidate every time (ETag -> 304), the service worker logic is unchanged, the edge answers from Manila instead of going to origin, and the next `firebase deploy` purges it. Leave `pantas_sw.js` on plain `no-cache` (worker update checks must hit fresh bytes; with purge-on-deploy it would also be safe, but there is no need to touch it).
- Gain: ESTIMATED from the measurements above: ~40-60 ms per file typical, removes 0.2-0.7 s tails. Return visit chain touches 4-7 of these files in series (navigate -> parser-blocking head scripts -> flutter_bootstrap.js -> flutter.js -> manifests), so 0.15-0.4 s typical, up to ~1 s on a bad tail. First visit and after-deploy visits gain the same on main.dart.js TTFB.
- Cost on Blaze: none. Edge hits do not add Hosting transfer (same bytes delivered).
- Security impact: none. Static public files only; no user data passes Hosting (`/wrapped/**` goes to a function and is not covered by these rules).
- Risk and effort: 0.25 h config + one deploy, verify with `curl -I` twice for `x-cache: HIT`. Beta-safe yes, needs board no. Main risk is only that the purge-on-deploy behavior is relied on; it is documented Hosting behavior.

## F5. Put each build's Dart output in a versioned folder; then the 4 s worker wait can go, and after-deploy visits download main.dart.js in parallel instead of after the wait
- Where: web/flutter_bootstrap.js:7-12 awaits `registerWorker`; web/pantas_pwa.js:42-55 (4 s cap, only when a controller exists); web/pantas_sw.js:29-41 (PRECACHE omits main.dart.js), :64-71 + :220-229 (main.dart.js and parts are cache-first by bare path); tool/web/stamp_worker_version.mjs (existing post-build step, already computes a per-build hash).
- What happens now: same-build return visits pass the wait in milliseconds (`register()` with the same script URL does not refetch). The wait bites on the first visit after each deploy: the new worker must fetch 11 files with `cache: 'reload'`, install, activate and claim, up to 4 s; only then does Flutter request main.dart.js, which the new cache does not have, so 1.53 MB (2.1 s measured here) downloads after the wait. With several deploys a day during beta, most testers' first open of the day takes this path. The wait exists only because bare paths (`main.dart.js`, `main.dart.js_N.part.js`, `assets/...`) can be answered from the previous build's cache.
- Change: in the stamp step, move `main.dart.js`, its `*.part.js` files and `assets/` into `b/<version>/`, and set `_flutter.loader.load({config: {entrypointBaseUrl: 'b/<version>/', assetBase: 'b/<version>/'}})` in flutter_bootstrap.js. Verified in the built flutter.js: `load()` reads `entrypointBaseUrl` and joins it with `mainJsPath`; dart2js resolves deferred parts from `document.currentScript`, so parts follow main.dart.js. Add `firebase.json` header `/b/**` -> `public, max-age=31536000, immutable`, add `b/` to the worker's static prefixes, then stop awaiting `registerWorker` (call it after `load()`). An old worker can no longer serve a mismatched file because no new URL exists in its cache; it passes the request to the network.
- Gain: ESTIMATED 0.5-4 s on the first visit after each deploy (removes the wait), plus main.dart.js download overlaps worker install instead of following it (~1-2 s on 4G). Same-build return visits: ~0. First visits: immutable caching also saves the revalidation round trip on the second visit if the worker is gone.
- Cost on Blaze: Hosting transfer unchanged (same bytes, fewer 304 revalidations). Hosting storage keeps old `b/<v>/` only for the release that contains it, no growth.
- Security impact: none. Same files, same origin, no user data.
- Risk and effort: 3-4 h incl. testing deep links (`/home`, `/quiz/...` under the `**` rewrite: relative `b/<v>/` must be made absolute `/b/<v>/` because the page can load at a nested path), offline open, and Safari. Beta-safe yes if tested on staging first; needs board no.
