## F1. The existing warmer warms module loading, not the first real data request
- Where: `functions/src/keepWarm.ts:6–39` → seven parallel OPTIONS requests; `_core.ts:10–14` loads compiled Dart only when called; `_options.ts:21` sets maxInstances only.
- What happens now: 5-minute preflights target beta, roadmap, settings, entitlement, availability, insights, and content. They do not execute callable bodies, Firestore queries, or compiled planning logic. They do not guarantee an instance survives or cover scale-out. WARMUP_ENABLED defaults false in source; the brief says it is live, but deployed parameter/settings were not inspected.
- Change: retain this inexpensive best-effort warmer. Measure first authenticated POST separately from preflight. Do not add unauthenticated handler bypasses. If cold beta/roadmap still dominate, consider minInstances=1 only for those two after measuring; do not blindly warm all seven with paid idle instances.
- Gain: ESTIMATED 0 s when already warm, potentially 2–5 s on an otherwise cold call, constrained by the supplied production cold/warm measurements; first visit after idle/deploy remains exposed to lazy initialization even with preflights.
- Cost on Blaze: 30 days gives 8,640 schedule executions + 60,480 OPTIONS = 69,120 requests/month (3.46% of 2M). One Scheduler job is $0 if within the three free jobs, otherwise $0.10/month. At 0.1 s per OPTIONS and 0.3 s per scheduler execution, roughly 8,640 active instance-seconds/month, before cold starts, with no Firestore reads by OPTIONS. At 1 CPU/256 MiB, illustrative gross compute is $0.213 and request charge $0.0276 before free allowance. Optional minimum instances cost about $8.10/function/30-day month gross idle at 1 CPU/256 MiB, hence $16.20 for two, before credits and active-time differences. Do not promise a $0 idle bill.
- Security impact: none. Keep App Check, auth, replay protection and rate limiting unchanged.
- Risk and effort: 1–2 hours to instrument/check deployment, beta-safe yes; minInstances is a paid operational choice, needs board no.

The seven audited functions specify region/enforcement but no memory, CPU, concurrency or minimum-instance overrides. `_options.ts:21` caps instances at 10. Source comments and Firebase documentation establish the intended default: 256 MiB, 1 vCPU, concurrency 80, minimum zero. Confirm deployed Cloud Run settings before treating that as production fact. The cap is per service, so seven endpoints can scale separately; it is not a project-wide budget cap.

Retain these settings for beta unless CPU/memory/queue measurements justify a change. Node's synchronous JSON parsing and compiled-Dart calculations share one event loop across up to 80 in-flight requests; more concurrency does not create more compute. The generated Dart source is only 196,948 bytes on disk, products JSON 1,770 bytes and exam catalog 4,122 bytes (read-only wc measurement). F2's broad module graph is real but tiny JSON files alone cannot explain seconds of latency.

A 256→512 MiB increase keeps the default at 1 CPU and adds $0.000000625 per active instance-second, or $0.0625 per 100,000 seconds, if duration stays equal. With minInstances=1 it adds ~$1.62 gross idle/month. It is not a general CPU-speed fix. Explicit 1→2 CPU adds ~$0.000024/active second ($2.40/100,000 s) before credits, and single-threaded core code may not get faster. Reducing concurrency 80→10 changes the default service ceiling from 800 to 100 simultaneous requests with maxInstances=10, and can increase cold instances/queueing. There is no fixed dollar delta without a traffic/duration distribution. Instrument first (1–2 hours, $0 application calls/reads added if using existing logs), then benchmark any change outside this read-only audit. No resource change is recommended as a free guaranteed gain.

### Pricing basis and limitations

All dollar figures are USD, illustrative gross marginal charges BEFORE free allowances, taxes, transaction retries and bandwidth. Cash cost can be $0 while capacity is consumed. Firestore examples use the publicly displayed Standard regional baseline $0.03/100k reads and $0.09/100k writes. The web pricing tool exposes the default Iowa table, not a verified pantas-prod billing SKU/database location. For an actual read rate R and write rate W, multiply the stated read/write amounts by R/0.03 and W/0.09 respectively. Numeric operation counts remain useful regardless. Do not present these examples as an observed Singapore invoice.

Cloud Run request-based examples use $0.000024/vCPU-s active, $0.0000025/GiB-s memory and $0.40/million requests. Idle minimum calculation: 2,592,000 seconds × ($0.0000025 CPU + 0.25×$0.0000025 memory) = $8.10 per 30-day month before credits. This agrees with Firebase's approximate $8/month example for 256 MiB/1 CPU. Concurrency means billed instance-time is not always the sum of individual request durations. Free compute is shared at billing-account scope; the 2M request allowance does not imply all compute/egress is free.

The brief says 10 GB/month Hosting transfer; current Firebase pricing lists Hosting transfer as 360 MB/day and storage as 10 GB. Treat the brief's transfer budget as a planning constraint, but verify the actual daily billing allowance. No recommendation here adds Hosting transfers. Content callable payloads use backend egress; native signed packages are not in web startup. Egress dollar savings cannot be priced faithfully without response byte counts, destination tier and remaining allowance; F8 supplies a byte-volume example instead of inventing a bill.
