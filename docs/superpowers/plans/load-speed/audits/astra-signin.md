# Google sign-in diagnosis: 7 November 2026

Read-only source audit against the supplied production evidence. Findings below distinguish confirmed code behavior from unverified production causes.

Source HEAD verified: `571eea1aa875152a1ff4d63734fa83353ff379ce`. Paths below are relative to `/Users/aedwon/Documents/Projects/Pantas-wt-vc-fixes-r1`. Likelihood refers to this incident, not certainty that a code branch exists. No production root cause is yet proven.

## H1. Google finishes, but the popup result never reaches the original iPhone app (likelihood: high)
- Evidence for / against: `lib/core/auth/firebase_auth_gateway.dart:147-171` uses only `linkWithPopup` / `signInWithPopup` for web Google sign-in. `lib/core/auth/auth_repository.dart:195-197,243-245` treats popup closure/cancellation as cancellation; `lib/app/sign_in/email_sign_in_page.dart:204-216` silently leaves the email screen on cancellation, shows only a generic message on failure, and has no timeout for a pending future. This exactly permits the reported outcome after Google has issued a security email. An iOS standalone-to-browser hand-off, lost opener/event channel, or inaccessible auth storage is a plausible mechanism, not a behavior proven by this source audit. The absence of `recordSignInEvent` at 09:16–09:17 supports failure before repository completion. Home data at 09:17:10–12 means at least one context progressed; it does not identify the original window or account.
- How to confirm: On the affected device, establish Safari tab versus installed standalone app and whether OAuth returns to the same context. Capture a correlated attempt's popup outcome/error code, original-window UID/isAnonymous before and after, and whether the popup promise settles. Inspect opener/event delivery and auth-helper storage access in that same run. A completed popup result and named session in the original window rule out a lost hand-off for that attempt. Compare Safari and installed-app behavior; a Google security email alone cannot establish Firebase completion.
- Fix: If confirmed, implement a supported same-context redirect flow with redirect-result recovery and preserved account-link intent, or an explicitly supported Safari sign-in flow for standalone users. Validate storage and helper-origin behavior before selecting the fallback. Surface popup cancellation/failure and provide email-code recovery. Do not blindly change authDomain or assume redirect alone repairs all iOS storage restrictions.

## H2. Existing-account collision falls back to a second popup after signing out (likelihood: medium)
- Evidence for / against: `lib/core/auth/auth_repository.dart:185-205` links an anonymous user first, then switches on `credential-already-in-use` or `email-already-in-use`. `lib/core/auth/firebase_auth_gateway.dart:168-169` saves a credential only for the first error, and it may be null. Lines 159–164 consume that credential or open another popup. `auth_repository.dart:225-235` awaits preparation and the identity hook, signs out, then invokes that fallback. A second popup can occur after the original user gesture, or its result can be lost as in H1. Failure can restore an anonymous session (`:241-247`) and leave plain email entry. Against: when a usable pending credential exists, the code explicitly uses `signInWithCredential`, avoiding the second popup, and signOut does not clear that field (`firebase_auth_gateway.dart:85-91`). The earlier 08:07 usage suggests a returning visitor but does not establish whether their current session was anonymous or which Google account was chosen.
- How to confirm: Capture link error code, whether a pending credential exists (never token contents), completion of prepare/hook/signOut, and whether a second popup or credential exchange is used. Reproduce with an existing Google account from an anonymous session. A non-null credential and successful credential exchange rule out the second-popup explanation; a popup-blocked/cancelled result after the collision confirms it. Also distinguish unhandled provider/account-conflict errors from the two accepted collision codes.
- Fix: Preserve and consume the provider credential for supported collision cases. If unavailable, request a fresh explicit Google-button gesture rather than opening another popup after asynchronous sign-out work. Keep or restore a usable session on transition failure and show the actual recoverable error category. Avoid treating every account conflict as a safe automatic merge.

## H3. Service worker serves the app shell in place of Firebase's auth helper (likelihood: low)
- Evidence for / against: This mechanism is specifically guarded against in this revision. `web/pantas_sw.js:61-80,146-153` bypasses `__/` before navigation handling, covering both `/__/auth/handler` and `/__/firebase/init.json`. The shell fallback at `:182-198` cannot run for those paths under this worker. Its opening comment that Firebase is always cross-origin is stale, but the executable bypass remains correct. A stale/different installed worker or incorrect deployed helper response remains possible; the supplied logs do not identify the worker or response body.
- How to confirm: Check the affected client's controlling worker URL/version and actual auth-helper responses. A Firebase helper response, rather than Pantas index HTML, rules this out. An index.html response attributed to an older worker, or a difference when bypassing that worker, confirms the variant. Check `/__/firebase/init.json` as both fetch and navigation, and `/__/auth/handler` / `/__/auth/iframe`.
- Fix: If an older worker is responsible, ship/activate the existing `__/` exclusion and retire the stale controller/cache. If the origin serves the app shell at these reserved paths, repair the Hosting/helper routing instead. Do not remove the working bypass or blame the navigation fallback solely because it exists.

## H4. The selected Google account signs in but is denied beta access (likelihood: low)
- Evidence for / against: `functions/src/betaAccess.ts:10-16` requires a non-anonymous provider, verified email, and a selected application matching the normalized token email. HTTP 200 does not establish `selected: true`. A different Google account can therefore be denied despite successful OAuth. However, `lib/app/beta_gate.dart:69-116` sends a named denied user to `EmailSignInPage(denied: true)`, and `lib/app/sign_in/email_sign_in_page.dart:471-479` renders `_NotOnList`, not the plain email form. Selected users awaiting Nov 9 receive `BetaWaitingPage` (`betaAccess.ts:6-7,33-36`; `beta_gate.dart:105-112`). A gate error has its own retry screen (`:87-102`). These outcomes do not match a literal unchanged email-input screen. Lack of a sign-in event also weighs against a fully completed normal sign-in, although H7 qualifies that inference.
- How to confirm: Correlate UID and token email/provider/email_verified with the exact `getBetaAccess` response and selected application. Record which view was visible: plain email entry, not-on-list message, waiting screen, or access-check error. A named denied account and `_NotOnList` confirm this explanation only if the reported screen description was imprecise. A selected response with no wait, or plain email entry with an anonymous session, rules it out as the sole cause.
- Fix: Use the intended selected Google account, or correct its application selection/email if appropriate. Refresh stale claims if that is what the trace shows. Preserve the distinct denial and waiting views; do not bypass the beta gate as an auth fix.

## H5. A stale sign-in hold keeps the gate on email entry (likelihood: low)
- Evidence for / against: `lib/app/beta_gate.dart:29,72` forces loading/EmailSignInPage while `signInHoldProvider` is true. But its initial value is false (`lib/app/sign_in/email_sign_in_page.dart:19`), and `_google()` (`:196-218`) never sets it. The email-code success timer releases it (`:290-300`), leaving code entry clears it (`:410-415`), and disposal clears it in a microtask (`:100-114`). A stale hold can theoretically hide a named session, but a fresh Google-only attempt has no direct path to enable it. No supplied log establishes a hold value.
- How to confirm: Read the hold value alongside Firebase session, authStateProvider, route, and page phase during the failure. False rules it out. True after a prior code attempt, with a named selected user and no remaining verification/celebration, confirms the stale-hold mechanism. Distinguish that from a pending popup, whose busy state is separate.
- Fix: If reproduced, bind the hold to the active code attempt and ensure every cancellation/error/disposal releases only that attempt's hold. Add bounded recovery for a genuinely abandoned operation. Do not add a Google hold merely to address this symptom.

## H6. COOP or history mutation breaks the OAuth return (likelihood: low)
- Evidence for / against: The app's declared headers in `firebase.json:44-108` are Cache-Control only; no COOP header is configured there. This gives no source evidence of app-configured `Cross-Origin-Opener-Policy: same-origin` severing the popup channel. Actual upstream/served headers remain unknown. `web/index.html:67-68` loads `pantas_history.js` in the app shell. That script (`web/pantas_history.js:13-28,35`) runs once, recognizes a Flutter `{serialCount,state}` wrapper and replaces only history state while preserving the full current URL. It does not navigate, strip OAuth query/hash data, or manipulate window.opener. It should not execute in a correctly served Firebase helper document. If it appears there, investigate H3/helper routing first.
- How to confirm: Inspect actual opener/handler response headers and popup-channel errors for the affected attempt. A restrictive COOP policy with demonstrably lost communication supports the header variant; a console warning alone does not. For the history variant, capture document URL and history state before/after the script and determine whether Firebase needs state that was replaced. Normal helper documents without this script and preserved opener communication rule these out.
- Fix: If an actual restrictive app COOP header causes the failure, adjust that served policy to one compatible with the chosen OAuth popup flow (for example, evaluate same-origin-allow-popups), then validate the complete chain. If history state is proven to be overwritten, exclude auth hand-off contexts or narrow the Flutter-state check. No blanket removal of the history helper is justified by the current code.

## H7. Account-switch preparation or post-auth event recording fails or stalls (likelihood: medium)
- Evidence for / against: `lib/core/auth/auth_repository.dart:225-239` awaits transition preparation and the payment identity hook before sign-out/exchange, then awaits `recordSignInEvent` before returning success. Preparation is outside its AuthGatewayException catch. `lib/core/sync/runtime/sync_account_transition_gateway.dart:13` delegates to quiesce; `sync_runtime_controller.dart:169-184` awaits local state clearing and a queued engine stop. `lib/features/paywall/application/revenuecat_bootstrap.dart:37-41,169-170` installs a hook that awaits clearIdentity. A failure there after a successful Google link-collision response leaves the existing anonymous session and no event request. Separately, successful linking at `auth_repository.dart:191-201` can be reported as failed when the subsequent event call fails. `firebase_auth_functions_gateway.dart:41-42,67-79` propagates callable errors. A client-side failure before dispatch can explain no Cloud Run event request; a server-side failure should normally leave a request log. Against: a successful Firebase exchange remains signed in even if event recording fails, and the reactive beta gate can already move to Home. Therefore event failure alone is a weaker explanation for persistent plain email entry than preparation failure. The later email-code success shows shared transition/event infrastructure worked at 09:19; it does not exclude an earlier transient failure.
- How to confirm: Trace start/end/error for prepareForAccountSwitch, beforeIdentityChange, signOut, popup/credential exchange, and recordSignInEvent using one attempt ID. A stall before exchange confirms the preparation variant. A named Firebase session followed by event failure confirms false failure reporting, but explaining the plain email form also requires checking gate state/context. Successful completion of all these stages rules this hypothesis out. Distinguish HTTP request logs from stored audit rows: `functions/src/recordSignInEvent.ts:28-32` throttles audit writes to once per hour, but still receives and returns from each callable request.
- Fix: Repair the particular failing preparation dependency and give stalled work a controlled recovery path while preserving identity-isolation guarantees. After authentication succeeds, report event-recording failure separately and retry it; avoid presenting an already signed-in user as an auth failure. This callable also creates the user record and public ID (`recordSignInEvent.ts:18-27`), so do not simply discard it as optional analytics.

## H8. The original context loses or never observes the Firebase session (likelihood: medium)
- Evidence for / against: `lib/app/firebase_bootstrap.dart:54-58` initializes Firebase but sets no explicit auth persistence. No `setPersistence` call was found under `lib/`; this means reliance on SDK behavior, not proof of memory-only persistence. `lib/app/auth_bootstrap.dart:67-75` ensures an anonymous session on startup, and `lib/core/auth/auth_repository.dart:89-92` does so only when currentSession is null. If a context reloads without recovering the named session, plain email entry is expected. A separate Safari/PWA storage context or a later sign-out could also reconcile Home traffic at 09:17:10–12 with email entry afterward. `lib/firebase_options_prod.dart:51-56` uses `app.pantas.study`, reducing the basis for assuming a cross-origin auth helper in the current build; an older live client may differ. Against a simple same-UID-link notification bug: `firebase_auth_gateway.dart:26-28` deliberately uses idTokenChanges on web, and `auth_state.dart:30-42` classifies the updated isAnonymous field. `providers.dart:24-25` and `beta_access.dart:80-83` consume those changes. None of these files establishes a persistent stream failure.
- How to confirm: Correlate per-context UID/isAnonymous, runtime authDomain/build version, token events, reload/background events, persistence restoration, and actual selected Google account. Compare the original app with the OAuth browser context without exposing tokens. A successful named session only in another context, or a named-to-null/anonymous transition after reload, supports this cause. A stable named session and emitted SignedInAuthState in the original window rule out session loss and direct attention to H4/H5/routing. Verify that the 09:17 Home requests share that context and UID before treating them as proof of a successful Google attempt.
- Fix: For demonstrated persistence failure, initialize supported durable persistence before auth operations and report failures with a recovery path. Resolve startup ordering only if a trace proves anonymous bootstrap races restoration. For separate browser contexts, use a supported hand-off that completes in the intended context. For missing stream propagation, repair the observed stream/provider boundary; do not replace the existing web idTokenChanges fix without evidence. Confirm the current authDomain and Firebase helper configuration in the actual deployed client.
